# MOLT product baseline

Source: [product discussion](https://chatgpt.com/share/6ace211b-a838-83e8-9d77-f4a436e48b09), final naming decision: **MOLT**. *Shedding legacy. Reborn in Rust.* Agent-native Rust rewrite engine: less abstraction, less infrastructure, more Rust.

## Design commitments

- Interface: Rust CLI with bounded JSON output + portable Agent Skill for Pi, Codex and Claude Code; no built-in LLM, API key, MCP server, browser dashboard or agent extension.
- Inputs: JS/TS (including React/Node), Java/Spring, whole monorepos. Original source is read-only except for local, gitignored MOLT state. Rewrite output stays separate.
- Workflow: discover → reason/simplify → approve → rewrite → verify → package/deploy → report. **Simplify source-system overengineering**, then build well-structured, idiomatic target Rust without weakening its engineering practices. Preserve observable behavior and distinguish evidence from inference.
- Intended output stack: Rust/Dioxus/WASM frontend, Axum/Tokio backend, SQLx/PostgreSQL, Redis as optional cache, PostgreSQL chunked binary media storage, OCI + Helm for single-node k3s/Traefik. Target architecture is a proposal requiring workload-specific validation, not a guarantee.
- Destructive migrations, data deletion, service merges, breaking changes and real deployment require explicit human approval. Charts alone do not prove deployability.
- SQLite stores rebuildable codebase intelligence (indexes, future semantic graph, findings, tasks, verification). Important approvals/plans belong in version-controlled artifacts. Queries must be bounded and traceable to source; incremental reindexing must account for affected dependents when semantic analysis is added.

## Implementation status / roadmap

| Stage | Scope | Status |
|---|---|---|
| 0 | Rust workspace, JSON CLI, JS/TS/Java file hashes + local SQLite, incremental upsert/removal, bounded file query, portable skill | Implemented (file inventory only) |
| 1a | Oxc JS/TS/JSX/TSX syntax parser; top-level declarations with line spans and static imports/re-exports; parse status and bounded SQLite queries | Implemented; no type/call resolution |
| 1b | Relative static JS/TS import resolution and reverse file edges; nested symbols, alias/package resolution, affected-dependent semantic invalidation | File-level relative edges implemented; rest planned |
| 1c | Syntax-derived GraphQL SDL root fields, literal Spring HTTP routes and heuristic JS/TS HTTP calls with candidate path matches; bounded coverage-issue diagnostics | Implemented as limited inventory; no Java type attribution, no verified call graph |
| 2 | Project semantic IR, FTS5/search, contextual queries, findings, persistent tasks/decisions, resumable analysis versions | Planned |
| 3 | Rules/checks and scaffold, reproducible Rust verification with behavior/contract baselines and structured diagnostics | Planned |
| 4 | OCI packaging, Helm templates, opt-in deployment and smoke tests, performance/compatibility report | Planned |

The syntax index is **not** a type checker, complete endpoint extractor, verified dependency graph or working converter. Java `parse_status: unsupported` refers to type/semantic analysis: Tree-sitter can separately inventory literal `@RestController` mapping paths but not their runtime reachability or inherited mappings; OpenRewrite type-attributed analysis is planned. Parsed JS/TS declarations are limited to named top-level functions, classes, variables with simple identifiers, TS interfaces/type aliases/enums; imports include `export ... from` and resolve only conservative relative file paths. Resolution is recomputed on every scan so added/deleted targets update edges even if the importer has not changed; this is **not** semantic dependent invalidation. Non-relative package/alias imports, non-code assets, dynamic import/require, destructuring and nested declarations are out of scope. GraphQL inventory reads standalone `.graphql`/`.gql` SDL or non-interpolated `gql`-tagged templates from any JS/TS binding; client GraphQL operations are ignored. It records root Query/Mutation/Subscription fields. Heuristic outbound HTTP candidates are literal `this.get/post/put/delete/patch` arguments under **any** JS/TS directory; without type resolution, these method calls may not actually be HTTP clients. Template strings and dynamic routes are omitted. HTTP path/method joins are labeled `path_match_unverified`, not proven cross-service links. `contract_status`/`contract_errors` track parser or unsupported annotation cases; `contract-issues` exposes bounded, source-located diagnostic codes (a null line means no precise location is available; a non-null line identifies the construct start, not necessarily the precise error). Class-level Spring method restrictions are intersected with method-level mappings; unknown/dynamic mappings are skipped rather than invented. `contract_issues: 0` does **not** mean complete contract coverage. Syntax diagnostics are counted, not persisted as full messages. No original code is stored in SQLite. Evaluate supply-chain, licensing, crates.io/GitHub name and trademark availability before public release; `molt` availability is not confirmed.
